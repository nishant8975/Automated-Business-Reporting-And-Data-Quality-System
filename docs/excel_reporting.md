# Excel Reporting Layer

This document details the architecture and generation of the Automated Business Report in Excel.

## Output Locations & Archiving
- **Latest Report**: `reports/excel/automated_business_report.xlsx` (Always represents the latest successful pipeline run).
- **Historical Archive**: `reports/excel/archive/automated_business_report_YYYY-MM-DD_HH-MM-SS.xlsx`.

Each successful pipeline run generates a new timestamped copy in the archive directory, while updating the latest report. Failed or partially generated workbooks are not archived.
## 1. Purpose
The purpose of the Excel reporting layer is strictly presentation and visualization. It provides a professional, analyst-oriented workbook that consumes the validated `analytics` views from PostgreSQL.

## 2. Workbook Structure
The workbook consists of the following 9 worksheets:
1. **Executive Summary**: A dashboard-style layout displaying top-line KPI cards, monthly GMV trends, category performance, and order status distributions.
2. **Monthly Sales**: Monthly performance time-series data and charts.
3. **Category Analysis**: Sales and volume sliced by product category.
4. **Payment Analysis**: Order and transaction volumes by payment method.
5. **Customer Analysis**: Customer behavior, including One-Time vs. Repeat purchase summaries.
6. **Review Analysis**: Customer satisfaction distribution.
7. **Order Status**: Fulfillment health distribution.
8. **Data Quality**: High-level summary of records quarantined or flagged in earlier pipeline stages.
9. **Source Data**: Documentation of the PostgreSQL views used in the workbook.

## 3. PostgreSQL Source Views and KPI Sourcing
**PostgreSQL analytics views are the single source of truth for core business KPIs.** Excel is used for reporting and visualization rather than independently recalculating transactional KPIs. 

- The Executive Summary does not run a pivot aggregation over raw data. Instead, it pulls directly from `analytics.v_order_kpis`.
- Data for charts and tables are mapped directly from corresponding views:
  - `analytics.v_monthly_sales` -> Monthly Sales
  - `analytics.v_category_sales` -> Category Analysis
  - `analytics.v_payment_analysis` -> Payment Analysis
  - `analytics.v_customer_analysis` -> Customer Analysis
  - `analytics.v_review_analysis` -> Review Analysis
  - `analytics.v_order_status` -> Order Status
  - `analytics.v_data_quality_summary` -> Data Quality

## 4. Fan-Out Prevention
No worksheet attempts to flatten the grain. Excel explicitly avoids joining disparate grains (e.g., `orders`, `order_items`, `order_payments`). All granular aggregation is handled entirely by PostgreSQL's independent CTE architecture, guaranteeing protection against cartesian joins (fan-out).

## 5. Formatting Approach
- Monetary values retain their exact source precision and are formatted cleanly using standard accounting rules (thousands separators, two decimal places) where applicable. 
- Date/Month information is formatted consistently for time-series charts.
- Percentages are appropriately formatted out of 100%.
- Clean spacing, clear column headers, and native Excel tables are used to present tabular data.

## 6. Reconciliation Checks
During workbook generation, a Python script validates that the final loaded dataset matches exactly with the core PostgreSQL assertions:
- Executive GMV = `analytics.v_order_kpis.gmv`
- Category Total GMV = `analytics.v_order_kpis.gmv`
- Monthly Total GMV = `analytics.v_order_kpis.gmv`
- Payment Total = `analytics.v_payment_analysis.total_payment_value`
- Customer Total Orders = `analytics.v_order_kpis.total_orders`

## 7. Known Limitations
- The Excel file is static. It acts as a snapshot generated by `create_excel_report.py`.
- Dynamic drill-through is limited since the workbook avoids importing row-level transactional databases to prevent file size bloat and incorrect aggregation.
